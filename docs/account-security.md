# 암호화 키 관리와 계정 보호

## 사용자 기능

- 보안·처리 이력 → 계정 보호에서 현재 비밀번호를 확인하고 인증 앱을 등록합니다. 시간 기반 TOTP(SHA1, 6자리, 30초)를 지원합니다. 등록 키는 외부 QR 서비스에 보내지 않으며 앱에 수동 입력합니다.
- 설정은 10분 안에 같은 로그인 세션에서 앱의 실제 코드를 확인해야 완료됩니다. 설정 이후 로그인과 인감·삭제 등 민감 작업 승인에 코드가 필요합니다. 서버는 성공한 시간 구간의 코드를 다시 받지 않습니다. 다음 코드를 기다리거나 복구 코드를 사용하세요.
- 복구 코드 8개는 발급 시 한 번만 표시됩니다. 서버에는 무작위 80비트 코드의 SHA-256 해시만 저장합니다. 각 코드는 한 번만 사용 가능하며, 재발급하면 이전 코드는 전부 폐기됩니다. 비밀번호 관리자 등에 별도 보관하세요.
- 비밀번호만 맞은 MFA 로그인은 5분짜리 일회용 요청을 반환하며 인증 세션을 발급하지 않습니다. 추가 인증은 계정·접속원별 시도 횟수 제한을 적용합니다.
- MFA 설정·해제, 복구 코드 재발급, 비밀번호 변경은 기존 세션·민감 작업 승인·대기 중인 추가 로그인을 폐기하고 현재 브라우저에만 새 세션을 발급합니다. 복구 코드로 로그인해도 기존 세션을 폐기합니다.
- MFA 해제·복구 코드 교체에는 현재 비밀번호와 기존 앱 코드 또는 복구 코드가 필요합니다. 분실했다는 이유로 비밀번호만 확인하고 MFA를 해제하는 API는 없습니다. 앱과 복구 코드를 모두 잃은 경우 자동 복구는 지원하지 않습니다.
- 새 비밀번호는 12자 이상, UTF-8 72바이트 이하입니다. 기존 비밀번호는 로그인 호환성을 유지합니다. 이미 탈취된 세션은 모든 기기 로그아웃으로 폐기할 수 있습니다.
- 보안 이력에 MFA 등록·활성화·해제·인증 실패·복구 로그인·비밀번호 변경이 기록됩니다. 실시간 이메일/새 기기 탐지 알림과 강제 관리자 MFA는 이번 구현에 포함하지 않았습니다. 운영자는 관리자 MFA 등록을 별도 확인해야 합니다.

## 키 보관

운영 키는 DB, Git, 문서 출력, 로그에 넣지 마세요. `SECRET_KEY`와 데이터 암호화 키는 별개입니다. 다음 중 **하나만** 설정합니다.

- `DATA_ENCRYPTION_KEYS`: 비밀 관리 서비스에서 주입한 Fernet 키 목록(새 키 우선, 쉼표 구분).
- `DATA_ENCRYPTION_KEY_FILE`: Secret volume 등으로 마운트한 키 목록 파일의 절대 경로. 파일 내용도 새 키 우선 쉼표 구분입니다. 심볼릭 링크, 빈 파일, 중복·잘못된 키는 거부합니다. POSIX에서는 파일 권한 0600 등으로 그룹·다른 사용자 접근을 차단해야 합니다. Windows에서는 서비스 계정과 승인된 관리자만 접근하도록 NTFS ACL을 별도 설정하세요. 상위 경로·Secret volume 권한도 보호해야 합니다.

명시적으로 지정한 키 소스에 문제가 있으면 새 키로 대체하지 않고 실패합니다. 로컬 개발에서만 기존 `storage/.data-encryption.key` 자동 생성 방식을 유지합니다. 기존 키 파일을 지우거나 덮어쓰지 마세요. 키 백업은 DB 백업과 별개로 보호합니다.

이는 관리형 Secret 주입/파일 연동 지원입니다. 특정 클라우드 KMS API를 연결하거나 영업 담당자가 문서를 볼 수 없는 종단간 암호화를 구현한 것은 아닙니다. 서버 실행 권한을 탈취당하면 복호화될 수 있으므로 운영자·서비스 계정의 접근 권한도 제한해야 합니다.

## 키 교체 절차 (server 디렉터리)

아래 명령은 키 값과 문서 본문을 출력하지 않습니다. 키 값 대신 SHA-256 기반 식별자로 설정을 비교합니다.

```powershell
..\.venv\Scripts\python.exe scripts/manage_keys.py status
```

1. 모든 서버·작업자의 쓰기를 중단하고 복구 가능한 DB/원본 백업과 현재 키의 별도 백업을 확인합니다. 해당 백업에서 복호화가 되는지 먼저 확인하세요.
2. 승인된 비밀 관리 서비스에서 새 Fernet 키를 생성하고 `[새 키, 기존 키들]` 순서로 설정합니다. 기존 키를 제거하지 마세요. 모든 인스턴스를 재시작해 동일한 키 집합을 읽도록 합니다. 키 소스 변경은 실행 중인 프로세스에 자동 반영되지 않습니다.
3. 새 키 집합으로 DB 암호화 필드(MFA 비밀 포함)와 등록된 로컬 원본·HWPX 파생 원본을 재암호화합니다. 로컬 파일은 검증 후 원자적으로 교체합니다. 쓰기는 계속 중단한 상태여야 합니다.

```powershell
..\.venv\Scripts\python.exe scripts/manage_keys.py rotate --backup-confirmed --writes-paused
..\.venv\Scripts\python.exe scripts/manage_keys.py verify
```

4. 검증은 실제 저장된 암호문을 주 키 하나로 읽어 DB와 등록된 원본이 모두 새 키를 사용하는지 확인합니다. 실패하면 모든 기존 키를 유지하세요. 파일과 DB를 묶은 단일 트랜잭션은 아니므로 중단 시 같은 키 집합으로 재실행합니다. 파일을 구형 키로 되돌리는 대신 백업 복구 절차를 따릅니다.
5. 실제 조회·다운로드·MFA를 점검한 뒤 쓰기를 재개합니다. 백업과 과거 파일에 이전 키가 필요할 수 있으므로 `verify` 성공만으로 이전 키를 삭제하면 안 됩니다. 검증 범위에 백업·이메일·다운로드 사본은 포함하지 않습니다. 백업 만료/재암호화와 복구 검증이 끝난 뒤에만 이전 키를 폐기합니다.

교체 명령은 기존 DB 데이터를 변경하므로 자동 실행하지 않습니다. 제공업체 키 생성·권한 부여·키 폐기는 승인된 운영 절차로 진행합니다. 코드 배포만으로 키가 교체되지 않습니다.

## 스키마 반영 및 검증

- 로컬은 서버 재시작 시 기존 데이터를 유지하면서 MFA 전용 테이블 3개가 생성됩니다. 실제 계정의 MFA를 자동 활성화하지 않습니다.
- 클라우드는 새 코드 배포 전에 `docs/security-schema.sql`의 추가 테이블을 DB 관리자가 반영해야 합니다. SQL은 `CREATE TABLE IF NOT EXISTS`를 사용하며 앱 계정에 DDL 권한을 부여하지 않습니다. 새 테이블도 기존 backend 전용 RLS 정책을 따르며 사용자별 RLS를 구현한 것은 아닙니다.
- 최신 추가 SQL 생성: `DATABASE_SCHEMA=capstone` 환경에서 `python scripts/migrate_security.py --schema-sql`. Windows에서는 `$env:DATABASE_SCHEMA='capstone'`으로 설정합니다. 운영 DB 연결 문자열이나 키를 명령 기록에 직접 적지 마세요.
- 이 작업에서는 클라우드 설정, 운영 DB, 실제 키, 실제 사용자의 MFA를 변경하지 않았습니다.
